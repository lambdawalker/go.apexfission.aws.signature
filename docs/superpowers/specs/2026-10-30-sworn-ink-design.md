# Sworn Ink signature infrastructure — approved design

Scope: new Android signing library and Go/AWS verification service. User approved JWT integration, hardware-backed signing, negotiated policy, replay protection, evidence storage, KMS receipts, and pluggable independent timestamps. JWT issuance and email verification are external. No infrastructure deployment or package publication is authorized by implementation.

## Architecture and alternatives
External configurable JWT issuer was selected over a dedicated Cognito directory to avoid duplicate identity infrastructure. Account identity is the exact trusted issuer and subject, never email. No runtime client can select an issuer. API Gateway JWT authorizer enforces issuer/audience and access-token scopes; Lambda refuses events without authorizer claims. Local tests use injected identities, not an insecure network bypass.

Signing suites are ES256_STRONGBOX and ES256_TEE, in that server preference order. Both use P-256/SHA-256; hardware protection distinguishes them. Capabilities are advisory. Registration attestation must prove the selected suite; no automatic client fallback after selection. Network cryptography is TLS; S3 evidence encryption is SSE-KMS. Application encryption negotiation is outside this signing protocol.

## Protocol v1 (authoritative in Go repository)
All HTTP JSON binary values use standard padded base64; digests use lowercase SHA-256 hex. Certificate chain is leaf-first DER encoded as an array of base64 strings. Signature bytes are ASN.1 DER ECDSA, not JOSE r||s.
POST /v1/challenges body: operation (register or sign), suites (array of suite strings), keyId (required for sign), documentSHA256 (required for sign). Return challengeId, nonce (32 random bytes base64), suite, expiresAt (Unix seconds), and statement (base64; present for sign). Five-minute validity. Registration attestation challenge is decoded nonce.
POST /v1/registrations body: challengeId, certificateChain, signature. Server computes leaf SPKI fingerprint (keyId) and registration statement. Client derives the same keyId locally and builds that statement.
POST /v1/signatures body: challengeId, document (base64), signature. Server independently hashes document and reconstructs statement, loads key bound to JWT issuer/subject, and verifies signature. Maximum document 512 KiB.

Statement is concatenation of UTF-8 fields, each preceded by unsigned 32-bit big-endian byte length: `sworn-ink/v1`, operation, suite, challengeId, nonce (its standard padded base64 text), issuer, subject, keyId, documentSHA256 (empty for registration). SHA256withECDSA signs these exact bytes. No JSON canonicalization ambiguity and no prehash double-hashing ambiguity. The Go low-level VerifyDocumentHash API verifies a precomputed SHA-256 digest directly, without hashing it again. Android production signing uses the complete protocol statement, not a bare hash.

## Verification
Trust comes only from operator-supplied reviewed Google hardware attestation roots; never from request roots or OS web PKI. Support Google's rotating roots through configuration. Validate full X.509 path, times, constraints, P-256 public key, attestation challenge, attestation/keymaster hardware levels, hardware-generated origin, signing purpose, EC algorithm/curve/digest, biometric-only per-operation authorization, absence of noAuthRequired/authTimeout, locked verified boot and allowlisted application package AND signer digest. Reject malformed/duplicate security tags and untrusted/malformed app IDs. Check every verified chain serial against fresh Google attestation revocation status; fetch failure or stale data fails closed. Enrollment invalidation is requested locally; do not claim the attestation explicitly proves that flag. Android hardware tests are required for real enforcement.

## Persistence and failure semantics
DynamoDB stores pending challenges (expiresAt enforces five-minute authorization; ttlAt retains recovery state for seven additional days before eventual cleanup) and registered keys; conditional transaction consumes registration challenge and creates key. Signing atomically claims challenge before writing evidence. Evidence is a single JSON bundle containing document, signature, exact statement, registration evidence references, receipt and validation details, written to deterministic evidence/<challengeId>.json with create-only S3 semantics. Conditional completion records track status. Retry of exact same request may finish a claimed operation; different bytes cannot replace it. Cross-service atomicity is impossible: incomplete evidence remains pending and is never reported as verified completion. KMS signs receipt hash. RFC3161 is an injected interface; absent provider is explicitly unavailable, never represented as independently timestamped. No fake TSA implementation.

## Operations and scope
Pulumi Go provisions HTTP API/Lambda, DynamoDB, SSE-KMS versioned private S3, receipt signing key and least privilege IAM. Retention configurable; do not default to irreversible compliance retention. Root trust, app allowlist, issuer/audience/scopes and AWS region are operator inputs. Go deployment tooling provides S3 state, SSO locally/OIDC in CI, saved configuration, encrypted local secrets and hash-based build reuse; deployment requires explicit selection. No email challenge and no account creation endpoint.

Documentation: owning repos maintain APIs and en/es Development guides, raw agent Markdown and generated HTML; Go owns shared protocol and architecture with reciprocal Android links. No invented published releases. Android UI is the OS BiometricPrompt; no custom Compose surface or fabricated screenshot suite. Instrumentation/manual device scenarios prove platform flows; host tests prove statement encoding. Security claims are scoped to verified evidence, not legal identity or enforceability.
